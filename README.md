# Агент возвратов магазина «Вольт»

Агент читает письма и обращения из чата, сопоставляет их с покупками отправителя и применяет правила P1–P10 из набора данных. Денежная операция в этом задании — запись о возврате в локальном состоянии.

## Как проверить тестовое задание

1. **Начните с исходных 13 обращений R01–R13.** В задании опубликованы восемь эталонов. Для остальных пяти можно сопоставить текст обращения, политику и решение агента. [Условие задания](task_requirements/TASK.md) · [Обращения, заказы и политика](task_requirements/data.json)
2. **Проверьте сохранённые результаты без API-ключа.** Из корня репозитория выполните `uv run --locked python eval.py`. Для комплекта в `out/` ожидаются `8/8` совпадений и успешная проверка финансовых инвариантов для всех 13 решений. В результатах приведены ответы клиентам и заметки сотрудникам, в реестре — проведённые операции. [Результаты](out/results.json) · [Реестр возвратов](out/refunds.json)
3. **Проследите решение до записи в реестре.** В R02 агент вызвал `create_refund` и вернул 1 180 ₽ за два кабеля. В R09 сумма 86 990 ₽ осталась в `proposed_refund_total` до согласования. В R08 агент передал обращение неизвестного отправителя сотруднику до вызова модели. [R02](out/traces/d02f394826584b91a13580690016f5e1/case_R02.jsonl) · [R09](out/traces/d02f394826584b91a13580690016f5e1/case_R09.jsonl) · [R08](out/traces/d02f394826584b91a13580690016f5e1/case_R08.jsonl) · [Тесты обезличивания](tests/test_privacy.py) · [Известное ограничение защиты ПДн](#известное-ограничение-защиты-персональных-данных)
4. **Проверьте повторяемость.** Выполните команду для свежего прогона из раздела «Запуск» дважды с одним выходным каталогом. ## Запуск

Понадобятся [uv](https://docs.astral.sh/uv/getting-started/installation/), доступ к RouterAI и API-ключ с положительным балансом. Версия Python указана в `.python-version`. На Windows проверена установка CPython 3.10.20 и зависимостей Natasha из `uv.lock`. Локальные языковые модели входят в пакет.

После клонирования создайте локальный `.env` командой PowerShell `Copy-Item .env.example .env`. Для живого прогона укажите в нём свой `ROUTERAI_API_KEY`. URL и модель заданы в образце. Git игнорирует `.env`.

```powershell
uv run --locked --env-file .env python main.py
```

По умолчанию вход — `task_requirements/data.json`, выход — `out/`. В комплекте уже есть состояние проверенного прогона. Команда выше воспроизводит его без обращений к модели. Для свежего прогона через RouterAI укажите свободный каталог, например `out-review`.

```powershell
uv run --locked --env-file .env python main.py --out out-review
```

Параметр `--data <файл>` принимает другой набор той же версии политики. Храните `state.json` вместе с выгрузками выбранного каталога.

## Как принимается решение

Один Python-процесс обрабатывает обращения по `received_at`. Для каждого нового обращения он создаёт отдельный контекст. Отправителя устанавливает по `from_email`. Если его нет в базе, сотрудник получает вопрос для уточнения по P8, сетевых вызовов нет.

1. **`get_case_context()`** передаёт модели очищенный текст, политику, дату, разрешённые заказы этого клиента и остатки по их позициям.
2. **`assess_return(intent)`** принимает тип просьбы, заказ, SKU, количество, описание причины, признак других реквизитов и неопределённость. Для позиции нужна дословная цитата из очищенного текста. Python сверяет её с источником, заново устанавливает область заказа и проверяет правила. Цитата помогает найти ошибку интерпретации. Сама модель всё ещё может неверно понять просьбу.
3. **`create_refund()`** доступен после разрешающей оценки. У инструмента нет параметров. Он перепроверяет ту же оценку по актуальному состоянию и возвращает результат зафиксированной операции. При отказе или эскалации обработка завершается. Ответы клиенту и сотруднику формируются локальными шаблонами.

Хост проверяет порядок, запрещает одновременные вызовы и допускает одну попытку исправить структуру. Бюджет — шесть вызовов инструментов на обращение. Таймауты HTTP конечны, для временных ошибок предусмотрен один повтор. Ошибка ключа, сервиса или повреждённого состояния завершает запуск с техническим кодом. Правила P1–P10 реализованы для отпечатка версии `policy` из задания. Изменение политики требует проверки реализации перед обработкой.

### Деньги и состояние

Суммы в исходном формате — целые рубли. Для каждой строки код умножает `paid_unit_price` на положительное целое количество, затем складывает строки. Стоимость доставки, бонусы и каталожная цена в эту формулу не входят. Остаток включает все исторические и новые возвраты. Дубли SKU, неоднозначные позиции и просьбы сверх положительного остатка уходят на уточнение. Автоматический возврат разрешён до `meta.auto_refund_limit` включительно, способ оплаты копируется из заказа.

Дата расчёта берётся из `meta.as_of`. День доставки — нулевой, четырнадцатый день входит в окно P1. Для гарантии код прибавляет календарные месяцы. Если нужного дня в последнем месяце нет, гарантия действует по последний день месяца включительно.

`out/state.json` хранит исходную историю, новые операции и результаты всех решений. Хеш базовых данных исключает обращения и golden, поэтому в тот же набор можно добавлять новые обращения. Под короткой межпроцессной блокировкой хранилище перечитывает файл, проверяет хеши запроса и действия, повторяет денежные проверки и записывает операцию вместе с решением через временный файл и `os.replace`. Обе выгрузки строятся из этой версии состояния под той же блокировкой. Подтверждение `create_refund` выдаётся после выгрузки.

Повтор того же входа получает сохранённое решение до запуска NLP и LLM. Другой вход под прежним ID вызывает конфликт. При сбое между фиксацией и выгрузкой следующий запуск восстанавливает JSON. Если история пропала при наличии следов прогона или повреждена, программа останавливается. Сохраняйте резервную копию состояния. Гарантия порядка относится к одному последовательному запуску на локальной файловой системе.

### Персональные данные и трассы

До первого сетевого вызова локальный PrivacyGate применяет словарь всех известных клиентов, шаблоны контактов и платёжных реквизитов, Natasha NER и AddrExtractor. Совпадения заменяются метками. Отдельный признак передаёт установленное различие назначения платежа. Перед каждой HTTP-попыткой проверяется фактически сериализованное тело, включая вложенный JSON, историю инструментов и их схемы. Неудачная очистка или потеря значимого смысла передаёт случай сотруднику. Вложенные инструкции клиента остаются данными. Веб-поиск и плагины провайдера не используются.

В `out/traces/<run_id>/case_<request_id>.jsonl` сохраняются вызовы, безопасные проекции аргументов и ответов, причины и итог. Для текста хранится хеш, для цитаты — координаты. Каждому повтору соответствует свой каталог. Тесты перехватывают тело запроса на уровне HTTP-транспорта и независимо проверяют отсутствие известных значений. Автоматическое распознавание может пропустить новое или замаскированное имя и адрес. Хеш обращения также требует защиты от доступа посторонних.

## Ограничения и допущения

### Известное ограничение защиты персональных данных

При дополнительной локальной проверке обнаружен пропуск короткого телефонного номера в свободном тексте. Например, в синтетическом обращении с фразой `Телефон для связи 555-73-21` номер сохраняется после очистки и проходит проверку сериализованного HTTP-запроса. Проверка выполнялась без отправки запроса внешнему провайдеру.

Текущая защита сочетает словарь известных клиентских данных, регулярные выражения, Natasha NER и AddrExtractor. Однако общий шаблон телефона не покрывает этот формат, а повторная проверка использует те же механизмы распознавания и не обнаруживает пропуск. Поэтому обязательное требование об отсутствии ПДн в запросах к LLM для этого класса входных данных пока не обеспечено.

Сравнение и внедрение дополнительных способов локального распознавания оставлены за рамками текущей итерации тестового. Следующий шаг — добавить обнаруженный случай и его варианты в регрессионные проверки, расширить набор новых контактов и адресов, сравнить детекторы и проверить сохранность бизнес-смысла после очистки. Критерии проверки — пропуски ПДн, ложные срабатывания и сохранение товара, количества и причины возврата.

### Границы реализации и принятые допущения

- **Смысловой разбор зависит от модели.** Модель извлекает товар, количество, причину возврата и другие признаки просьбы. Код проверяет структуру, принадлежность заказа, остатки, правила и денежный расчёт. Проверка дословной цитаты подтверждает наличие фрагмента в обращении, но не является независимым доказательством правильности его интерпретации.
- **Поддерживается конкретная версия политики.** Правила P1–P10 реализованы кодом для `policy` из задания. При изменении её содержимого обработка останавливается. Поддержка новой политики требует проверки и при необходимости изменения реализации.
- **Состояние рассчитано на локальную файловую систему.** Идемпотентность и защита конкурентной записи работают для процессов, использующих общее состояние и файловую блокировку. Порядок обработки по `received_at` обеспечивается внутри одного последовательного запуска. Распределённая обработка на нескольких узлах не реализована.
- **Возврат означает запись в реестре.** В соответствии с заданием `create_refund()` фиксирует локальную операцию. Интеграция с платёжным провайдером не входит в реализацию. Для неё потребуются ключ идемпотентности провайдера и сверка фактического исполнения при потере ответа или неопределённом сетевом результате.
- **Для R03 принята рабочая трактовка.** Просьба перечислить деньги на другую карту передаётся сотруднику по P5/P10. Для этого обращения опубликованного эталона нет. Перед промышленным использованием такую трактовку нужно согласовать с владельцем политики.
- **Результат eval относится к предоставленному набору.** Совпадение 8/8 относится к опубликованным эталонам; всего обработано 13 обращений. Проверки финансовых инвариантов дополняют score, но не измеряют полноту распознавания ПДн или качество понимания всех новых формулировок. Для оценки обобщения нужен отдельный, заранее размеченный набор обращений.

## Перед промышленным запуском

1. Согласовать с владельцем политики неоднозначные запросы вроде R03 и собрать независимый размеченный набор переформулировок.
2. Проверять приватность на новых форматах контактов и реквизитов, ограничить доступ к трассам, задать сроки хранения и добавить ручной разбор подозрительных фрагментов.
3. Для нескольких узлов ввести транзакционный журнал, порядок обработки по заказу и проверенное восстановление из резервных копий.
4. При подключении платёжного провайдера использовать его ключ идемпотентности и сверять фактическое исполнение с локальной записью.
