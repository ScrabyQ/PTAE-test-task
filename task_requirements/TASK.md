# Тестовое задание: агент обработки заявок на возврат

**Роль:** агентный инженер
**Время:** 1,5–2 часа. Больше тратить не нужно: если не успели, опишите в README, что бы сделали дальше.
**Язык и стек:** любые. Рекомендуем Python.
**LLM:** любая (облачная или локальная), ключ ваш. Если доступа к LLM нет, напишите нам до начала, предложим вариант.

---

## Легенда

Интернет-магазин электроники «Вольт» получает от клиентов обращения на возврат: по почте и в чате, свободным текстом. Сейчас их вручную разбирает сотрудник: находит клиента и заказ, сверяет с политикой возвратов, оформляет возврат или отказ.

Нужен агент, который разбирает обращение и принимает одно из трёх решений:

| Решение | Что делает агент |
|---|---|
| `refund` | Оформляет возврат денег (создаёт запись о возврате) и готовит ответ клиенту |
| `reject` | Не оформляет возврат, готовит ответ клиенту с причиной по политике |
| `escalate` | Не оформляет возврат, передаёт обращение сотруднику с причиной и, если нужно, с вопросом клиенту |

Цена ошибки высокая: лишний возврат — прямые потери, ошибочный отказ — недовольный клиент. Поэтому агент должен быть **точным и осторожным**: если не уверен, он передаёт обращение человеку, а не угадывает.

---

## Данные

Всё лежит в одном файле **`data.json`**:

| Раздел | Содержимое |
|---|---|
| `meta` | Текущая дата для расчётов (`as_of` = 2026-11-10), лимит автоматического возврата |
| `policy` | Политика возвратов, правила P1–P10. **Единственный источник правил** |
| `catalog` | Товары: цена по прайсу, гарантия, можно ли вернуть |
| `customers` | Клиенты, включая персональные данные |
| `orders` | Заказы: дата доставки, способ оплаты, позиции с **фактически оплаченной** ценой |
| `refunds` | Уже оформленные возвраты |
| `requests` | 13 обращений R01–R13. Обрабатываются по порядку `received_at` |
| `golden` | Эталонные решения для 8 из 13 обращений. Остальные 5 мы проверим сами |

Дату «сегодня» берите из `meta.as_of`, а не из системных часов.

## Что нужно сделать

### 1. Инструменты
Реализуйте доступ агента к данным через **инструменты (tools)**. Набор и их сигнатуры выбираете вы. Возврат должен создаваться через отдельный инструмент, который сохраняет запись в `out/refunds.json` (по образцу `refunds` в данных).

Реализация в виде MCP-сервера — плюс, но не обязательна.

### 2. Агент
Агент обрабатывает все 13 обращений и пишет результат в `out/results.json`, по одному объекту на обращение:

```json
{
  "request_id": "R01",
  "decision": "refund | reject | escalate",
  "order_id": "O-1001 или null",
  "policy_rules": ["P1"],
  "refund": {
    "lines": [ { "sku": "KTL-200", "qty": 1, "amount": 4990 } ],
    "total": 4990,
    "method": "card **** 4417"
  },
  "proposed_refund_total": null,
  "message_to_customer": "текст ответа клиенту (для refund и reject)",
  "note_for_staff": "причина и вопрос клиенту (для escalate)"
}
```

- `refund` заполняется только при `decision = refund`, в остальных случаях `null`.
- `proposed_refund_total` — только если обращение передано на согласование из-за суммы.

### 3. Обязательные требования
1. **Деньги и реквизиты.** Суммы, количество и способ возврата в результате должны быть гарантированно корректны. Опишите в README, как вы это обеспечили.
2. **Персональные данные.** ФИО, email, телефоны и адреса клиентов не должны попадать в LLM, ни из базы, ни из текста обращений. Ответ клиенту при этом должен остаться осмысленным.
3. **Повторный запуск.** Если весь прогон запустить второй раз, новых возвратов появиться не должно. Повтор вызова инструмента (например, после таймаута) тоже не должен создавать дубль.
4. **Политика.** Агент следует только правилам из `policy`.
5. **Трассировка.** Для каждого обращения сохраняйте лог шагов: какие инструменты вызваны, с какими аргументами, что вернули, какое решение принято. Формат свободный, в `out/traces/`.

### 4. Eval
Напишите скрипт, который сравнивает `out/results.json` с `golden` и печатает:
- сколько обращений совпало;
- по каждому несовпадению — что ожидалось и что получилось.

Сравнивайте `decision`, `order_id`, строки и сумму `refund`, `proposed_refund_total`. Текст ответа клиенту сравнивать не нужно.

### 5. README (≈20 минут, кратко)
- Как запустить (одна команда) и что нужно для запуска.
- Архитектура: что решает модель, что решает код и почему так.
- Результат eval и разбор каждой ошибки, если они есть.
- Какие обращения показались вам рискованными и как агент их обрабатывает.
- Что вы добавите перед запуском в прод (3–5 пунктов).

## Как будем оценивать

- Корректность решений, включая обращения, которых нет в `golden`.
- Надёжность там, где ошибка стоит денег.
- Граница ответственности между моделью и кодом.
- Качество инструментов: описания, схемы, ответы, ошибки.
- Защита персональных данных.
- Честность eval и README: ошибки, найденные и описанные самостоятельно, ценим выше, чем идеальную цифру.

После сдачи — созвон на 30–40 минут: разберём решение и прогоним агента на паре новых обращений.
